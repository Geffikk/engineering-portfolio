Cross-venue arbitrage platform

A self-hosted platform that continuously compares prices for the same sporting fixture across two independent classes of venue, detects two-leg arbitrage, and places both legs automatically under code-enforced risk limits. Running in production with real money.

What it does

Same fixture, two venues, opposite outcomes

The system ingests live prices from sportsbooks and from an on-chain prediction-market exchange, works out which listings refer to the same real-world fixture, prices the two opposite outcomes, and places both legs automatically under hard, code-enforced risk limits.

INGEST

Prices in

WebSocket odds streams, exchange order-book deltas, and headless Chromium for venues with no API.

MAP

Pair the fixture

No shared identifiers, no shared naming. Deterministic fuzzy matching plus a curated alias library.

DETECT

Price the edge

Publish when the two opposite outcomes leave a margin above the floor, with a reason recorded when they do not.

ADMIT

Score the worst case

Revalidate on fresh prices, score after fees, FX, rounding and slippage, apply budgets and exposure caps.

EXECUTE

Place both legs

Browser plus captured authenticated request on one side, fill-or-kill CLOB orders on the other.

SETTLE

Prove the outcome

Named terminal state, measured fills only, per-row FX, and an explanation for every gap.

Architecture

State ownership is the whole design

Execution model

How a job is executed safely

An arbitrage exists only while both legs exist. The two venues are unrelated systems with different latencies and different failure modes, and no transaction spans them. Everything below exists so that a partial failure is survivable, visible and recoverable.

Single writer

All execution state is written by one Lua script running server-side inside Redis. Admission, budget checks, phase transitions and command emission happen in one atomic operation, so a check-then-act race across processes cannot occur.

Fencing tokens

Every fixture carries a fence, and every claimed resource carries its own. A worker must present the fence it was issued, so a stalled worker that resumes late fails its write instead of overwriting newer state.

Idempotent triggers

A repeated trigger returns the original job envelope rather than creating a second job, and a duplicate result delivery is recorded and acknowledged without changing authority state.

Proved emission

“A command was decided” and “a command was emitted” are two separate recorded facts, written in the same atomic operation. A scheduled audit asserts that they always agree.

Pure decision functions

Sizing, worst-case scoring, hedge repricing, flatten sizing and terminal-state classification take no clock, no network and no database. They are deterministic functions of their inputs.

Frozen replay corpus

A committed corpus pins real end-to-end outcomes down to authority phase, exposure, command lineage and economics. Any change to execution semantics fails CI and names the invariant that moved.

Job lifecycle

Every job ends in a named state

A job never ends as simply “failed”. It ends in one of a small set of explicit states, each carrying the evidence that produced it. This vocabulary is what makes the operator screens readable and automated recovery possible.

Terminal stateMeaningWhat follows
Completed Both legs filled at or better than the planned prices. Settlement and realized PnL are computed from the measured fills only.
Loss mitigated One leg was committed, the hedge was no longer viable, and the position was deliberately closed. Recorded as a known, bounded loss rather than left as an open position.
Open exposure One leg filled and the other did not, leaving real directional risk. The naked leg is named. Re-size and rescue run first; anything unresolved is surfaced to the operator and blocks further automation on that fixture.
Rejected A named gate refused the job: budget, margin, staleness, depth or duplicate. The reason is counted, so “why did nothing happen” always has an answer.
Unknown outcome A venue response was ambiguous, so the position is treated as possibly open. Reconciliation resolves it against venue records before the job is closed.
Risk and failure handling

Limits live in code, not in an operator’s memory

Per-plan and per-fixture budgets

One opportunity is capped, and so is total commitment to a single real-world event inside a rolling window.

Worst-case ROI floor

After fees, FX, rounding and slippage. A plan must be profitable in its worst case, never merely its expected one.

Never a negative worst case

Automatic execution may not knowingly accept a losing worst case. Hard zero.

Depth and staleness gates

Top-of-book depth must honour the protected price, and every input has an age ceiling. Stale fails closed.

Pre-submit hedge guard

Re-reads the hedge venue immediately before committing the first leg, and refuses if the hedge is no longer buyable.

Layered recovery

Re-size, then rescue into a balanced pair, then deliberate flatten, then escalate to a named open-exposure state that blocks further automation.

Bounded retries

Venue-driven backoff honouring retry-after hints, idempotent triggers, duplicate-result tolerance, and retry exhaustion as an explicit terminal state.

Per-venue kill switches

Every venue has a master enable flag and a paper-or-live submission mode. Paper simulates both legs with zero exposure.

rollout pattern for every new enforcement  →  off  →  shadow (measure what it would have done)  →  enforce
Delivery and operations

Merging to main is the deployment

Portainer GitOps polls the repository and redeploys the stack. There is no manual deploy script and no hand-edited file on the production host. One compose file is both the build contract and the deployment source, so what CI builds is literally what runs. Secrets live in the orchestrator, and the stack fails fast when one is missing, so a half-configured deploy never starts. Rollback is a revert plus a redeploy.

Monitoring runs as its own stack, because a monitor that dies with the thing it monitors is decoration: self-hosted metrics, live logs, Sentry-compatible error tracking, a notifier for crashes and a watchdog for absence. Alerts carry suppression windows so a normal deploy does not page anyone, recovery notices so an alert always ends, and a daily heartbeat.

The only public surface is the operator dashboard, behind an identity-allowlisted access proxy and an outbound-only tunnel, with application OAuth inside it. Every internal admin tool is reachable over VPN only.

Quick answers

The questions people actually ask

Live or paper?Live, with real money, under automated limits. Paper is a first-class per-venue mode, not an afterthought: one venue lane runs live, a second is fully implemented and deliberately still in paper pending its evidence review.
REST or WebSocket?Both, by role. WebSocket for live prices (order-book deltas, both odds streams). REST for catalog, discovery, settlement and order placement. Chrome DevTools Protocol for venues with no API.
Redis: cache, Pub/Sub or Streams?All three, deliberately separated. Streams with consumer groups for restart-safe pipelines, Pub/Sub for cheap fan-out that the next reconcile repairs, keyed live state guarded by Lua, and server-side Lua as the execution authority.
DatabaseMongoDB for durable history, mapping, audit and projections. Two separate Redis instances: rebuildable market state, and a durable replicated execution authority.
Scheduled workPer-service internal loops from versioned config, a scheduler sidecar for stack sleep and wake windows, and CI cron for read-only production audits. No external cron on the trading hot path.
AI in the loop?None. Fixture matching is deterministic fuzzy matching plus a curated alias library, because a trading decision has to be reproducible and auditable.
