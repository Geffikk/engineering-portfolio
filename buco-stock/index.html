Overview

The problem, and what I built

Deciding whether a share is cheap means reading the company’s own financial statements and doing the arithmetic yourself. Free screeners hand you a number without showing where it came from, so you cannot check it or argue with it. AI chatbots will confidently produce a valuation and cite a source that, often enough, does not say what the chatbot claims it says.

So I built the tool I actually wanted. It pulls financial statements directly from the US regulator’s filing archive, computes a valuation from them, and stores every input it used. Any number on the screen can be re-derived a year later and proven to be the same number, or shown to have changed and exactly why.

On top of that it does two more things. It asks commercial AI research products the same question and then checks their homework, verifying every factual claim against the page the report cited. And it imports my real brokerage positions read-only, so I can see what I hold next to what the engine thinks it is worth.

It is a single-user internal tool, in daily use. It has never placed a trade and there is no code in it that could. That is the point: a tool that helps you decide and a tool that executes are two different products with very different risk, and mixing them turns the first into the second.

How it works

From a company name to a number on screen

Six steps. The first three are pure arithmetic over official filings. The next two are where AI comes in, and where it is kept honest. The last one is what a person actually looks at.

1 · IDENTIFY

Pin down which company

A ticker is not an identity. “MC” returns four different issuers across the world’s exchanges. The company is resolved to a legal entity with a registered identifier before anything else happens.

2 · FETCH

Read the actual filings

Financial statements come from the SEC’s machine-readable filing archive. Not a data vendor, not a scraped website, and never a chatbot.

3 · COMPUTE

Value the business

Project future cash flow, work out the discount rate, and run the standard valuation models against it. Every input is recorded alongside the result.

4 · RESEARCH

Ask the AI products too

The same company is put to commercial AI research tools, which read the news, analyst notes and coverage that a filing does not contain.

5 · VERIFY

Check every claim

Each factual statement in those reports is traced back to the page it cited. The page is archived, the quote is located, and the claim is tested against it. Reports that fail are kept and shown as failed.

6 · PUBLISH

Show it against the price

The filing-based number, the verified research number and today’s market price sit on one screen, with the gap between them stated plainly.

This runs two ways. On demand, when I ask for a company, and automatically every night. The nightly job asks a simple question of every company being tracked: has anything changed that would make yesterday’s answer wrong? A new filing, an updated assumption, a newer version of the engine, or figures that have simply gone stale. Only those get recomputed.

Architecture

One server, and nothing on it is reachable from outside

Read the diagram in three columns: the edge on the left is how a visitor gets in, the dashed box in the middle is the server and everything running on it, and the right is where data comes from.

The direction of that first arrow is the whole security design. Nothing from the internet reaches the server. Instead a container inside the server dials out to Cloudflare and holds that connection open, and visitors are handed down the line that is already there. Like a call centre with no public phone number: staff call the switchboard, the switchboard passes callers through, and nobody can dial the building because there is nothing to dial. A port scanner sweeping the internet finds nothing.

The three workers are separate processes for a specific reason. A research run is ten to twenty minutes of waiting, so it cannot sit inside a web request. Running them as threads in one process does not work either, because the browser automation library cannot share one connection across threads. One process per source solved it: three sources run at once, and each source still has exactly one conversation going.

deliberate non-choices  →  no Redis / Celery / RabbitMQ  ·  no LLM vendor API  ·  no Kubernetes  ·  no CI runner  ·  no image registry

The one people ask about most is the queue. Background jobs live in MongoDB rather than in Redis or Celery, and a job is stored as an ordinary document that stays there after it has run. That is what makes “why did that one fail three days ago” a question with an answer. A broker would have bought throughput that a few dozen jobs a day will never need, in exchange for another container, another connection and a second place where the truth lives.

Deployment

How it ships and how it is run

Deploying is a push to main

Everything runs as Docker containers described by a single compose file, and Portainer on the server keeps that stack in sync with the repository. It polls the main branch every few minutes, and when the branch moves it pulls the new commit, builds the images on the server itself and recreates only the services that changed.

So pushing to main is the deploy. There is no CI pipeline and no image registry, and that is a simplicity decision rather than a gap: for a single-tenant tool on one host, a registry would mean publishing artefacts and managing credentials for them, and a CI service would mean a second place where the build can break. Rolling back is a revert and the next poll, and the commit that is actually live can be read straight off the running container.

Scheduled work

The nightly refresh runs from the server’s own scheduler, executing a module inside the already-running container. Deliberately not an HTTP endpoint, because that would mean storing a permanent admin password in a file on disk.

It asks one question of every company being tracked: has anything changed that would make yesterday’s answer wrong. It prints a summary of what it examined and what it recomputed, and exits with an error code if any company failed, so a scheduler watching exit codes notices without anyone reading the log.

Engineering

Three problems worth describing

Reproducibility

A number you cannot re-derive is just an opinion with a date on it

If the engine says a company is worth 41 dollars, I need to be able to ask that question again next year and know whether the answer changed because the company changed or because my code changed.

Every run stores the exact inputs it used, plus a fingerprint of them. Getting that fingerprint to mean anything took closing three loopholes: the same data written in a different field order, the same figure written as 1.10 or 1.1, and decimal numbers stored as binary floating point, where a tiny rounding error disappears from view.

Result. Replaying a stored valuation gives exactly three possible answers: nothing moved, the value moved because the code changed, or the fingerprint no longer matches the data, which means the record was tampered with. Nothing else in the system can detect that last one.

AI verification

The report checker was failing good reports, and lowering the bar would have hidden it

AI research reports are accepted based on how many of their claims can be traced back to the sources they cite. Reports started scoring 1 to 5 out of 12, and the obvious move was to lower the passing score.

That would have buried the real bug. The checker was reading only a fraction of each page’s sources, demanding both halves of a hedged estimate, and rejecting the same figure when it was written in millions instead of billions. The reports were mostly fine; my checker was wrong.

Result. After fixing it, the same tool on the same company scored 11 out of 12. The threshold went back where it belonged, and the screen now shows the score as a fraction so a reader can judge it without knowing a threshold exists.

Performance

A page spending two and a half seconds waiting on somebody else

The company listing took 2.70 seconds to load. Measuring it rather than guessing showed that 2.57 of those seconds were 42 price lookups fired one after another.

The fix was to serve the last known prices immediately and refresh them in the background, so nobody waits for data that was already good enough a minute ago.

Result. 2.70 seconds down to 0.19, and it stays that fast even after the cached data expires. One rule stops it lying: an empty response from upstream is never cached, because a slow reload beats showing “no companies” for a quarter of an hour.

Results

What it produces, and what it refuses to produce

The output is one screen per company: the value computed from filings, the value supported by verified research, the two blended, and today’s price beside them. There is an anonymized sample report using a fictional company that shows the real shape of it.

The clock, the network and the database are all swappable, so the test suite runs offline in seconds and never waits on a real service. Bug fixes ship with the failing test first.

The behaviour I am most pleased with is refusal. When the data is too poor to value a company, the tool says so and gives the reason, instead of producing a number nobody should trust. The same applies throughout: a missing exchange rate stops the calculation rather than defaulting to one, and a research report with an unverifiable claim is shown as failed rather than dropped so the scoreboard cannot flatter itself.

A tool whose whole job is producing a number is at its most dangerous when it produces one it should not have.
